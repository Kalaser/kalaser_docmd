# C语言编码规范

## 1. 明确作业范围和目的

### 1.1 范围

本规范适用于所有使用C语言进行的软件开发项目，包括但不限于系统软件、应用软件、嵌入式系统等。

### 1.2 目的

- 提高代码的可读性和可维护性
- 确保代码质量和一致性
- 减少编程错误，提高软件可靠性
- 促进团队协作和知识共享
- 便于代码审查和后续维护

## 2. 作业对象和适用人员

### 2.1 适用人员

- C语言开发工程师
- 代码审查人员
- 软件测试工程师
- 技术管理人员
- 维护人员

### 2.2 职责分工

- 开发工程师：负责按照本规范编写代码
- 代码审查人员：负责检查代码是否符合规范
- 技术管理人员：负责推广和监督规范的执行
- 维护人员：负责在维护过程中遵循规范

## 3. 作业流程和步骤

### 3.1 命名规范

#### 3.1.1 文件命名

- C源文件：使用小写字母，单词间用下划线分隔，如：`my_program.c`
- 头文件：使用小写字母，单词间用下划线分隔，以`.h`为扩展名，如：`my_header.h`

#### 3.1.2 函数命名

- 使用小写字母，单词间用下划线分隔
- 动词在前，名词在后，如：`calculate_sum()`
- 私有函数（仅在本文件内使用）可以添加`_`前缀，如：`_internal_function()`

#### 3.1.3 变量命名

- 使用小写字母，单词间用下划线分隔
- 全局变量：以`g_`开头，如：`g_global_variable`
- 静态变量：以`s_`开头，如：`s_static_variable`
- 常量：使用大写字母，单词间用下划线分隔，如：`MAX_SIZE`

#### 3.1.4 类型命名

- 自定义类型：使用`_t`后缀，如：`my_type_t`
- 结构体：使用小写字母，单词间用下划线分隔，以`_t`结尾，如：`person_t`
- 枚举：使用小写字母，单词间用下划线分隔，以`_e`结尾，如：`color_e`

### 3.2 格式规范

#### 3.2.1 缩进与空格

- 使用4个空格进行缩进，不使用制表符(Tab)
- 运算符前后加空格，如：`a = b + c`
- 逗号后加空格，如：`function(a, b, c)`
- 括号内侧不加空格，如：`if (condition)`

#### 3.2.2 大括号位置

- 函数定义：左大括号另起一行，如：
  ```c
  int function(void)
  {
      // code
  }
  ```
- 控制语句：左大括号不另起一行，如：
  ```c
  if (condition) {
      // code
  }
  ```

#### 3.2.3 行长度

- 每行代码长度不超过80个字符
- 如果超过，应在合适的操作符后换行，并对齐

#### 3.2.4 空行

- 函数之间空两行
- 逻辑相关的代码块之间可以空一行
- 函数内部逻辑块之间可以空一行，以提高可读性

### 3.3 注释规范

#### 3.3.1 文件头注释

每个源文件和头文件开头应包含以下信息：

```c
/**
 * @file filename.c
 * @brief 文件简短描述
 * @details 详细描述（可选）
 * @author 作者名
 * @date 日期
 * @version 版本
 */
```

#### 3.3.2 函数注释

每个函数前应有注释，说明函数功能、参数、返回值等：

```c
/**
 * @brief 函数简短描述
 * @param param1 参数1描述
 * @param param2 参数2描述
 * @return 返回值描述
 */
```

#### 3.3.3 行内注释

- 对复杂的代码逻辑进行解释
- 注释应放在代码上方，与代码对齐
- 避免使用`//`进行注释，统一使用`/* */`

### 3.4 声明与定义

#### 3.4.1 变量声明

- 变量应在使用前声明
- 局部变量应在函数开始处集中声明
- 变量声明时尽量初始化

#### 3.4.2 函数声明

- 所有函数应在头文件中声明，或在源文件开头声明
- 函数参数应使用有意义的名称，而不仅仅是类型

#### 3.4.3 结构体与联合体

- 使用`typedef`定义结构体和联合体类型
- 结构体成员应按逻辑分组，并添加注释

### 3.5 语句规范

#### 3.5.1 控制语句

- `if-else`语句：即使只有一条语句也应使用大括号
- `for`循环：循环变量应在循环内声明（C99及以上）
- `switch`语句：每个`case`后应有`break`，除非有意为之
- `goto`语句：尽量避免使用，除非在错误处理等特殊情况

#### 3.5.2 表达式

- 避免复杂的表达式，应分解为多个简单表达式
- 避免使用三元运算符代替简单的`if-else`
- 避免在表达式中使用自增/自减运算符，除非单独使用

### 3.6 内存管理

#### 3.6.1 动态内存分配

- 每次使用`malloc`、`calloc`、`realloc`后应检查返回值
- 动态分配的内存必须释放，避免内存泄漏
- 释放内存后应将指针置为NULL

#### 3.6.2 缓冲区安全

- 避免使用不安全的函数，如`strcpy`、`sprintf`等
- 使用安全的替代函数，如`strncpy`、`snprintf`等
- 确保缓冲区大小足够，避免缓冲区溢出

### 3.7 错误处理

- 使用统一的错误码定义
- 函数应返回错误状态，调用者应检查错误状态
- 错误处理代码应与正常逻辑分离
- 使用日志记录错误信息

## 4. 质量要求

### 4.1 代码质量

- 代码应通过编译器所有警告检查（使用`-Wall -Wextra`等选项）
- 代码应通过静态代码分析工具检查
- 代码应经过单元测试验证
- 代码覆盖率应达到80%以上

### 4.2 性能要求

- 代码应满足性能需求
- 避免不必要的计算和内存使用
- 在关键路径上优化性能

### 4.3 可维护性

- 代码应易于理解和修改
- 模块间耦合度低，内聚度高
- 遵循单一职责原则

## 5. 安全与环境要求

### 5.1 安全要求

- 避免常见的安全漏洞，如缓冲区溢出、整数溢出等
- 对所有外部输入进行验证
- 避免使用不安全的函数

### 5.2 环境要求

- 代码应兼容目标平台和编译器
- 考虑不同环境下的字节序、对齐等问题
- 避免使用平台特定的特性，除非必要

## 6. 设备和工具

### 6.1 开发工具

- 编译器：GCC、Clang或MSVC
- 代码编辑器：支持语法高亮和代码补全
- 版本控制：Git、SVN等

### 6.2 辅助工具

- 静态代码分析工具：如Cppcheck、Splint等
- 单元测试框架：如Unity、Check等
- 代码格式化工具：如clang-format、astyle等
- 文档生成工具：如Doxygen等

### 6.3 工具使用

- 使用版本控制系统管理代码
- 使用构建系统自动化编译和测试
- 使用持续集成工具自动化测试和部署

## 7. 记录与报告

### 7.1 代码审查

- 所有代码必须经过同行审查
- 使用代码审查工具记录审查意见
- 解决所有审查意见后才能合并代码

### 7.2 文档记录

- 所有公共API必须有文档
- 复杂算法必须有详细说明
- 维护变更日志

### 7.3 问题报告

- 使用问题跟踪系统管理Bug和功能请求
- 记录问题解决过程
- 定期分析问题趋势

## 8. 附录

### 8.1 代码示例

#### 8.1.1 文件结构示例

```c
/**
 * @file example.c
 * @brief 示例文件
 * @author Name
 * @date 2023-01-01
 */

#include <stdio.h>
#include "example.h"

/* 私有宏定义 */
#define MAX_VALUE 100

/* 私有类型定义 */
typedef struct {
    int id;
    char name[20];
} item_t;

/* 私有函数声明 */
static void private_function(void);

/* 全局变量 */
int g_global_var = 0;

/* 函数实现 */
int public_function(int param)
{
    int result = 0;
    
    if (param > 0) {
        result = param * 2;
    } else {
        result = 0;
    }
    
    return result;
}

static void private_function(void)
{
    /* 实现 */
}
```

#### 8.1.2 头文件示例

```c
/**
 * @file example.h
 * @brief 示例头文件
 * @author Name
 * @date 2023-01-01
 */

#ifndef EXAMPLE_H
#define EXAMPLE_H

/* 公共宏定义 */
#define PUBLIC_MACRO 100

/* 公共类型定义 */
typedef enum {
    COLOR_RED,
    COLOR_GREEN,
    COLOR_BLUE
} color_e;

/* 公共函数声明 */
int public_function(int param);

#endif /* EXAMPLE_H */
```

### 8.2 常见错误及避免方法

- 内存泄漏：确保每次分配都有对应的释放
- 空指针解引用：使用指针前检查是否为NULL
- 数组越界：确保数组访问在有效范围内
- 资源未释放：使用RAII模式或确保所有路径都释放资源
- 未初始化变量：声明时初始化或在使用前初始化
